# Задача кодеру: инвалидация цепочки сетапа при обновлении экстремума (пересвип)

Файл: `cisdbot.py` (md5 на момент постановки: `6dbfc29586eb6f7d263b46372e78cb15`).
Ветка SHADOW/paper, tf8 (30m → 8H), пары: BTC ETH DOGE KAS ADA BNB LINK LTC XRP SOL.

---

## 0. Что не так (факты, воспроизведено)

Кейс DOGE/USDT 17.09.2026:

| Время (МСК) | Что произошло |
|---|---|
| 13:00:12 | сигнал #1: окно свипа **08:00**, sweep 0.08132, entry 0.08113, stop 0.08166, tp 0.08060 → лимитка выставлена |
| 13:30:05 | скан выдаёт сигнал-«двойник»: окно свипа **00:00**, sweep 0.08098, **entry/stop/tp те же** → `SKIP pair busy` |
| 13:30:13 | первая лимитка отменена по таймауту (30 мин) |

Причина (проверено в коде и логе):
- кандидат свипа хранится по ключу `_cand_key(tf, direction, ОКНО)` и сравнивается **только сам с собой** (`_upsert_sweep_candidate`, ~стр. 4284): более глубокий свип в ДРУГОМ окне старый кандидат не снимает;
- живёт кандидат до `n_htf_keep` окон (tf8 = 2 окна = 16 ч), поэтому доживает до следующего окна, получает **чужой свежий триггер** (`детect: -> кандидат trigger сдвинут [окно]`, стр. 5076) и выпускает дубль-сигнал с уровнями от новой структуры;
- масштаб по бэк-потоку (`filters_off_full`, tf8, 2020–26): 483 пары сетапов с равным экстремумом триггера; стоп совпадает **483/483**, вход **482/483**, окно свипа — **0/483** (т.е. «новизна» второго сигнала — только служебная привязка к окну свипа).

---

## 1. Требуемое поведение

При появлении **более глубокого** свипа / триггер-экстремума по той же (пара, ТФ, НАПРАВЛЕНИЕ) — **в любом окне**, не только в своём:

1. **Старый кандидат — удалить** (`_drop_sweep_candidate`, reason вида `пересвип уровнем 0.08098 → 0.08132`).
2. **Неисполненная лимитка** от старого сетапа — **отменить**: в LIVE снять ордер на бирже (`_cancel_pending_entry`), `pl.status = "cancelled_resweep"`, `_journal_log_pending_cancelled(pl)`, TG-уведомление («ЛИМИТКА #N ОТМЕНЕНА — пересвип»). Освободить `htf_taken` / leg-lock / sweep-lock, чтобы новый сетап не получил `SKIP pair busy` (переиспользовать существующий путь освобождения, который срабатывает при `cancelled_timeout`).
3. **Открытая позиция — НЕ ТРОГАТЬ.** Никаких ручных закрытий: она закроется своим стопом (LIVE — стоп-ордер, paper — монитор).

**Порядок внутри одного скана:** сначала инвалидация (кандидат + лимитка + освобождение локов), затем решение о создании нового сигнала — чтобы более глубокая структура заняла место старой.

**Семантика сравнения (важно):**
- Глубина: SHORT — новый уровень/экстремум **строго выше** старого; LONG — **строго ниже**. **Равенство пробоем НЕ считается** — `>` / `<`, без `>=` / `<=`. Так же строго, как сейчас в `_pending_extreme_hit()`.
- Для TP/SL на бирже семантику **не менять** (там работает касание — как у стоп-ордера).

## 2. Точки правки (якоря)

| Что | Где |
|---|---|
| Снятие кандидата | `_drop_sweep_candidate()` (3810), `_cand_key()` (3720) |
| Создание/обновление кандидата | `_upsert_sweep_candidate()` (~4284) — **добавить сравнение со ВСЕМИ живыми кандидатами** той же (tf, direction, symbol) по разным окнам; при пересвипе снять старого |
| Сдвиг триггера кандидата | `_sync_cand_trigger()` (~4280) и блок с логом `кандидат trigger сдвинут` (5076) — триггер не должен «переезжать» в чужой/снятый свип |
| Инвалидация лимитки | `_pending_extreme_hit()` (~7730) + ветки `cancelled_extreme` (10200 и 11056) в `limit_monitor`; **не включать обратно** `_invalidate_pending_no_htf_inter_sweep` (4061/4095, отключён в `af790bc`) |
| Журнал/статистика | новый статус `cancelled_resweep` добавить в журнал лимиток и проверить группировки в `RUNS/temp/shadow_stats.py` и отчётах по `trade_logs/*.jsonl` |

**Ограничения:** минимальный дифф; LIVE-ветку ордеров, emergency-stop, детектор и пороги не менять; состояние решений (кандидаты/локи) должно переживать рестарт (см. патч `bc432a5` — персист `htf_sweep_lock`); мягкий режим проверки свипа (`окно не закрыто → пропускаем`) сохранить.

**Побочно (мелочь, но полезно):** в строки `детect: свип ...` и `детect: -> кандидат ...` добавить `symbol_key` и точность по тику — сейчас `:.1f`, из-за чего у DOGE/ADA/KAS всё выглядит как `0.1`/`0.2`.

## 3. Приёмка

1. **Юнит-тест:** кандидат окна A (уровень L1) → появляется кандидат окна B с более глубоким уровнем L2 → старый снят; при **равном** уровне — НЕ снят (строгое сравнение).
2. **Реплей DOGE-кейса:** на скане 10:00 UTC (13:00 МСК) при появлении кандидата окна 08:00 (0.08132) в логе должно быть `кандидат снят [2026-09-17 00:00:00] SHORT: пересвип уровнем 0.08098 → 0.08132`, и на 13:30 второго сигнала быть не должно.
3. **Живая проверка:** висящая лимитка при пересвипе реально отменяется на бирже (LIVE), в TG приходит уведомление; позиция не закрывается.
4. **Прогон по потоку 2020–26** (`RUNS/filters_off_full`, база: 26 015 сделок, ΣR +1642.7, ср. +0.063R): показать, сколько сетапов снимает правило и сколько ΣR. Ожидание — снимаются только «двойники» (стоп совпадает), потеря близка к нулю; если потеря существенная — вернуться с цифрами, не деплоить.
5. **Регресс:** `py_compile`, `RUNS/temp/test_paper_level_hits.py` (16/16), рестарт без Traceback, штатные сканы идут.

## 4. Что НЕ делать

- Не закрывать позиции вручную при пересвипе (правило 3).
- Не включать `_invalidate_pending_no_htf_inter_sweep` (снял 5056 сделок / ΣR +361R).
- Не считать равенство пробоем (кроме TP/SL на бирже).
- Не менять LIVE-ветку ордеров и emergency-stop.
